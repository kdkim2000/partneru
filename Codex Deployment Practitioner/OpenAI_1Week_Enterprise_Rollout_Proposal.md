## Day 3: 버그 진단 및 수정 프로세스

### 목표
- Codex를 활용한 체계적 버그 수정 워크플로우 확립
- 재현 → 진단 → 수정 → 검증 사이클 습득

### 활동 내용

#### 3.1 버그 A: 상태 필터링 오류 수정 (작업 2-A)

**재현 단계:**
```bash
curl http://127.0.0.1:8000/tasks
curl "http://127.0.0.1:8000/tasks?status=open"
```

**권장 프롬프트:**
> "GET /tasks 상태 필터 버그 재현, 근본 원인 설명, 최소한의 깔끔한 수정 구현, 결과 검증."

**수정 후 기대 결과:**
- `status=open` 파라미터 시 open 상태 작업만 반환
- 필터링 로직 정확성 보장

#### 3.2 버그 B: 완료 상태 지속성 문제 (작업 2-B)

**재현 단계:**
```bash
curl -X POST http://127.0.0.1:8000/tasks/1/complete
curl http://127.0.0.1:8000/tasks/1
```

**권장 프롬프트:**
> "완료된 작업의 지속성 문제를 재현하고, 저장소/비즈니스 로직 경계에서 수정하며, 지속성을 입증하기 위해 API 호출을 재실행하십시오."

**수정 후 기대 결과:**
- 작업 완료 상태가 재조회 시에도 유지됨
- `completed_at` 필드가 정확한 타임스탬프로 설정됨

#### 3.3 Codex 활용 5원칙 실천
1. **코드 변경 전 검사 요청** - 영향 범위 파악
2. **명령어 실행 위임** - 설정 및 검증 자동화
3. **발견 사항 설명 요청** - 근본 원인 이해
4. **Diff 검토** - 변경 사항 수락 전 확인
5. **재검증 요청** - 각 변경 후 동작 확인

## Day 4: 신규 기능 개발 및 통합

### 목표
- Codex를 활용한 요구사항 기반 기능 구현
- 기존 시스템과의 통합 검증
- 엔드-투-엔드 테스트 프로세스 확립

### 활동 내용

#### 4.1 검색 기능 구현 (작업 3)

**기능 요구사항:**
- GET `/tasks`에 선택적 `q` 쿼리 매개변수 추가
- 대소문자 구분 없는 검색
- 제목(title)과 설명(description) 필드 모두 검색
- 기존 `status` 필터와 조합 가능
- `q` 미제공 시 기존 동작 유지

**권장 프롬프트:**
> "GET /tasks에 대한 q 필터를 구현하여 제목과 설명에 대해 대소문자 구분 없이 일치시키고, q가 누락된 경우 기존 동작을 유지하며, curl로 검증하십시오."

#### 4.2 검증 시나리오
```bash
# 단독 검색
curl "http://127.0.0.1:8000/tasks?q=launch"
curl "http://127.0.0.1:8000/tasks?q=report"

# 필터 조합
curl "http://127.0.0.1:8000/tasks?status=open&q=plan"
```

#### 4.3 통합 테스트
- 단위 기능 테스트
- 필터 조합 시나리오 테스트
- 경계값 테스트 (빈 문자열, 특수문자 등)
- 성능 영향도 평가

### 성과물
- [ ] 검색 기능 구현 완료
- [ ] 모든 검증 시나리오 통과
