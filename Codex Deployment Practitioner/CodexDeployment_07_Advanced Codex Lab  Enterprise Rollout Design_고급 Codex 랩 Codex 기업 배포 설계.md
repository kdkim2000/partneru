# 고급 Codex 랩 — Codex 기업 배포 설계

*2026년 3월 생성*

---

## 1. 소개

이 랩은 "대규모 코덱스 운영화" 과정에서 배운 내용을 평가하기 위한 실습 과제입니다.

조직이 코덱스를 효과적으로 배포할 수 있도록 지원하는 롤아웃 설계 '원페이지'를 작성하게 됩니다.

**예상 소요 시간:** 30분에서 45분.

---

## 2. 시나리오

여러분은 중견 B2B SaaS 기업인 Linton Labs의 파트너로서, 소규모 파일럿에서 여러 엔지니어링 팀에 걸친 통제된 롤아웃으로 Codex를 확장하고자 합니다.

롤아웃은 실수가 고객에게 노출되는 청구서 오류로 이어질 수 있는 Linton Labs의 기존 청구 플랫폼에서 시작됩니다. 청구 저장소에는 불완전한 테스트가 있으며, 여러 엔지니어가 동시에 작업해야 하고, 회사는 더 광범위한 채택 전에 승인, 인터넷 액세스, 비밀 정보 및 감사 가능성에 대한 명확한 통제를 기대하고 있습니다.

**주요 이해관계자는 다음과 같습니다:**

- **마라:** AI 구현 책임자로, 팀이 신속하게 채택할 수 있는 롤아웃 패턴을 원합니다.
- **프리야:** 스태프 엔지니어로, 검토 혼란을 야기하지 않으면서 실제 배포 작업에 코덱스가 유용하게 활용되길 원합니다.
- **조나스:** SRE 책임자로서 클라우드 환경, 시크릿, 지원에 대한 안전한 기본값이 필요합니다.
- **레오:** 제품 책임자로서 피할 수 있는 운영 위험을 초래하지 않으면서 더 빠른 실행을 원합니다.

Linton Labs는 이미 Codex를 통해 개별 작업에서 유망한 결과를 얻었지만, 아직 공유 운영 모델을 갖추지 못했습니다. 표준 접근 방식을 정의하지 않으면 각 팀마다 서로 다른 인터페이스, 모델, 안전 장치를 선택할 수 있습니다.

---

## 3. 한 페이지 요약이 중요한 이유

실제 고객 출시 시 첫 번째 산출물은 긴 실행 계획이 아닌 경우가 많습니다. 경영진, 엔지니어링, 보안, 운영 팀 모두가 신속히 검토할 수 있는 간결한 설계입니다.

**원페이지 문서가 유용한 이유는 다음과 같습니다:**

- 모호한 모범 사례 대신 출시를 명확한 결정으로 이끌어 줍니다.
- 고객 관계자들에게 기본값, 가이드라인, 책임 소재에 대한 공통된 기준을 제공합니다.
- 파트너 팀이 심층적인 기술 구현 작업 시작 전에 초기 출시 단계를 조율할 수 있도록 지원합니다.
- 운영 검토, 지원 세션, 후속 설계 작업에서 재사용 가능한 가벼운 아티팩트를 생성합니다.

---

## 4. 제공물 (Deliverable)

**PDF 원페이지 문서 작성: "Codex 엔터프라이즈 롤아웃 설계".**

엔지니어링 리더십과 플랫폼 이해 관계자들이 리포지토리와 팀 전반에 코덱스를 도입하는 방법에 대한 명확한 권장 사항이 필요한 Linton Labs 출시 검토를 위해 이 문서를 준비한다고 가정합니다.

본 과정의 엔터프라이즈 롤아웃 패턴을 현실적인 시나리오에 적용합니다: Linton Labs가 청구 플랫폼을 시작으로 여러 저장소 및 팀에 Codex를 롤아웃하고, 이를 기반으로 안전하게 확장할 수 있도록 지원합니다.

**목표는 파트너사 준비 완료 상태의 롤아웃 설계를 작성하는 것으로, 다음을 충족해야 합니다:**

- 기본적으로 안전함
- 채택이 용이함 (마찰 최소화)
- 감사 가능하고 통제 가능
- 장기 실행 작업 및 장애 복구 가능

### 필수 섹션

#### 1. 표면 전략
- 각 팀이 기본적으로 코덱스 앱, IDE 확장 프로그램, CLI, 클라우드 중 어떤 것을 선택하는지 및 그 이유
- 워크트리가 필수인지 선택 사항인지
- 클라우드 작업이 필수(또는 금지)되는 시점
- Windows 환경 설정: 네이티브 Windows 샌드박스 모드(`unelevated` vs `elevated`), WSL 사용 시점, 그리고 관리자 권한 설정 차단 시 대체 방안

#### 2. 모델 전략
- 대부분의 작업에 대한 기본 모델
- API 키 워크플로우에 사용할 모델 (최신 사용 가능 모델 확인)
- 추론 노력을 확대해야 하는 시점
- 초저지연 루프에 Spark 적용 가능성(적용 불가 시점 포함)
- Spark 사용이 검증 요구사항을 어떻게 변화시키는가 (범위 축소 및 명시적 검증)

#### 3. 컨텍스트 연속성 플레이북
- 체크포인트 주기(체크포인트를 트리거하는 조건)
- 압축 정책 (압축 시기 및 결정 사항 보존 방법)
- 복구 패턴(실패한 시도, 드리프트, 스위칭 서피스, 스레드 재시작)

#### 4. 거버넌스 번들
- 구성 기본값(`config.toml`) 및 저장 위치
- 프로젝트 지침(`AGENTS.md`): 검증 명령어, 검토 가이드라인, "완료" 정의 포함
- 안전한 명령어 허용 및 위험한 명령어 차단 규칙(`.rules`)
- 고부가가치 워크플로우 표준화 기술 (예: "보안 PR 검토", "CI 수정 루프", "릴리스 노트")

#### 5. 클라우드 환경 정책
- 설정 스크립트 및 캐싱 접근 방식
- 시크릿 대 환경 변수
- 에이전트 인터넷 접근 정책 (기본 비활성화, 필요 시 허용 목록 적용)

#### 6. 통합
- GitHub 코드 리뷰 적용 방식 (수동 `@codex review` vs 자동 리뷰)
- Slack 및 Linear 사용 가이드라인 (위임 가능한 사항, 절대 위임 불가 사항)

#### 7. 관리 및 모니터링 계획
- 로컬 vs 클라우드 활성화 및 RBAC 그룹
- 추적할 거버넌스 신호 (분석 vs 규정 준수 로그)
- 지원 런북: 사용자 문제 발생 시 확인 사항 (승인, 샌드박스, 환경 선택, 접근 권한 부족)
- Windows 지원 점검: 관리자 권한 설정 필수 조건, 활성 샌드박스 모드, 로그인 경로/권한

*(모든 7개 필수 섹션의 "Click to complete" 체크 항목을 완료로 표시함)*

## 5. 제출 (Submission)

### PDF 업로드

**수락 기준**

1페이지 제안서에는 다음이 포함되어야 합니다:

- 최소 5가지의 명시적 결정 사항을 포함해야 합니다(단순한 설명이 아닌).
- 최소 3개의 가드레일(샌드박스 기본값, 규칙, 인터넷 접근, 비밀 정보)을 포함해야 합니다.
- 장기 실행 작업에 대한 복구 패턴 최소 2개 포함.
- "비밀 지식" 없이 구현 가능해야 합니다.

제출 후 검토를 위해 48시간 이내에 답변을 받을 수 있어야 합니다.

**제출 방법:** PDF 파일을 드래그 앤 드롭하거나 클릭하여 업로드
지원 형식: `.pdf`, `.mp4`, `.gif`, `.jpeg`, `.png`, `.zip`
